# Безопасность

Сервер даёт агенту доступ к кабинету AppGallery Connect от имени API-клиента. Ниже — какие границы держит сам сервер и что остаётся на стороне пользователя.

## От чего защищает сервер

- **Утечка учётных данных через агента.** Агент не получает секрет API-клиента, refresh token входа пользователя, секрет приложения и access token ни в одном ответе, ошибке или логе и не может передать их в аргументах инструментов.
- **Случайные отправки на проверку и изменения.** По умолчанию сервер только читает; запись и действия, которые видят пользователи AppGallery или которые затрагивают деньги, включает пользователь флагами.
- **Секреты из ответов API.** Секрет приложения, содержимое файла конфигурации, адреса и коды загрузки и временные ссылки на файлы вырезаются из ответов.
- **Произвольный доступ к сети и файлам.** `api_request` ходит только в AppGallery Connect API на хост региона профиля; файлы скачиваются и загружаются только на хосты Huawei; локальные файлы — только в разрешённых каталогах, существующие файлы не перезаписываются.

От чего сервер не защищает: от агента с доступом к оболочке на той же машине, который запускает команды от имени пользователя (он может, например, вызвать `appgallery-connect-mcp key exec`), и от API-клиента с ролями шире, чем нужно. Граница прав в кабинете — [роли API-клиента](api-client.md#роли); флаги доступа сервера сужают то, что агент делает через MCP.

## Учётные данные API-клиента и access token

- Client ID и секрет хранятся только в системном хранилище: macOS Keychain, Secret Service в Linux, Credential Manager в Windows. Запись: сервис `dev.filipov.appgallery-connect-mcp`, учётная запись — имя профиля. Запасного файлового хранилища нет. Единственное исключение — файл секрета у `serve --http` в контейнере ([HTTP-режим](#http-режим)).
- Секрет принимается только из файла (`--secret-file`), через stdin (`--secret-stdin`) или скрытым вводом в терминале. Он не принимается аргументом командной строки (там он остался бы в истории оболочки и списке процессов) и не читается из переменных окружения и `.env`. Путь к файлу секрета не запоминается.
- Ни одна команда не печатает секрет и access token: `auth status` и `serve --status` показывают только, сохранены ли учётные данные, и Client ID в маске. Команды, которая выводит секрет или токен, нет; `key exec` отдаёт их другой команде файлом ([key exec](#key-exec)).
- В конфигурацию MCP-клиента попадает только команда `appgallery-connect-mcp serve --profile <профиль> …`, в `profiles.toml` — регион, приложения по умолчанию и настройки доступа, без Client ID и секрета.
- Access token выпускается в памяти процесса сервера при первом запросе к API (`POST /api/oauth2/v1/token`, `client_credentials`). Huawei выдаёт его на 48 часов; сервер заменяет его новым за 10 минут до истечения и никуда не записывает. Получить токен через `api_request` нельзя.
- В памяти секрет и токен затираются после использования, в отладочном выводе они скрыты.
- Заголовки `Authorization` и `client_id` добавляет только сервер; `api_request` и заголовочные аргументы инструментов не могут их переопределить.
- Хост API выбирается только из списка регионов ([Регион и хост](api-client.md#регион-и-хост)); произвольный адрес не принимается, полные адреса, `..` и `//` в пути отклоняются.
- Один профиль — один API-клиент команды (и, если нужно, API-клиенты его проектов). Доступ любой машины можно снять, удалив её API-клиент в AppGallery Connect ([Отзыв доступа](api-client.md#отзыв-доступа)).

### API-клиенты проектов

Серверным API сервисов проекта нужен API-клиент уровня проекта ([API-клиент проекта](api-client.md#api-клиент-проекта)). Он хранится в том же профиле как отдельные учётные данные:

- Client ID и секрет клиента проекта — только в системном хранилище, учётная запись `<профиль>/project/<Project ID>`; в `profiles.toml` — только список Project ID (`projects`), без Client ID и секрета.
- `auth project add` читает файл `agc-apiclient-*.json` один раз и не запоминает путь: после команды файл можно удалить. Файл не больше 16 КиБ и только обычный файл; ошибки разбора называют строку и столбец, но не значения. Клиент сохраняется только после того, как по нему получен access token (если нет `--no-verify`).
- Секрет клиента проекта, как и секрет клиента команды, не принимается аргументом командной строки и не читается из переменных окружения.
- Сервер выпускает access token каждого клиента проекта отдельно, в памяти, тем же методом `POST /api/oauth2/v1/token` на хосте региона профиля, и заменяет его заранее. Клиент выбирает сервер, а не агент: по аргументу операции `productId` или `projectId`. Агент не может передать учётные данные или токен и не может направить запрос операции проекта на клиент команды и наоборот. `api_request` для пути такой операции выбирает клиент так же.
- Если клиента нужного проекта нет, запрос не отправляется, а агент получает ошибку с командой `auth project add`, которую пользователь запускает сам в терминале. В HTTP-режиме ошибка просит передать её оператору сервера: клиент проекта добавляется в профиль на машине сервера, а с `--secret-file` клиентов проектов нет.
- Ссылки App Linking (набор `app-linking`, уровень записи) публичные: их может открыть любой, кому они попали. Созданные через API ссылки не видны в AppGallery Connect, и API не умеет их перечислять, менять и удалять, поэтому набор выключен по умолчанию, а описание инструментов просит агента проверить ссылку до создания.
- Секреты и токены всех клиентов проектов вырезаются из ответов, ошибок и логов так же, как у клиента команды; `auth status` и `serve --status` показывают только Client ID в маске и сохранён ли клиент.
- `auth logout` удаляет клиенты проектов профиля вместе с клиентом команды; `auth project remove` — один клиент проекта.

### Вход пользователя

Профиль может работать от имени пользователя HUAWEI ID через OAuth-клиент ([Вход пользователя](api-client.md#вход-пользователя-oauth-клиент)):

- Client ID и секрет OAuth-клиента, refresh token и выданные области хранятся только в системном хранилище, учётная запись `<профиль>/oauth`. В `profiles.toml` — `type = "oauth"`, `team_id` и регион. Секрет OAuth-клиента принимается так же, как секрет API-клиента: файл, stdin или скрытый ввод.
- Вход в браузере защищён PKCE (S256) и случайным `state`. Команда слушает только 127.0.0.1 и только на время входа (до 5 минут). Она принимает код только с правильным `state` и на пути адреса возврата; другие запросы на этот порт вход не прерывают. Страница ответа браузеру — фиксированный текст без значений из запроса. Код, verifier, refresh token и access token не печатаются.
- Access token (живёт час) выпускается в памяти процесса сервера по refresh token и обновляется заранее. Новый refresh token, если HUAWEI ID его выдаст, записывается обратно в хранилище.
- Заголовки `oauth2Token` и `teamId` задаёт только сервер; агент не может передать или переопределить их ни в `api_request`, ни в аргументах инструментов. Команда берётся из профиля, а не от агента.
- Операции, которые справочник описывает только для API-клиента, сервер в этом режиме не отправляет.
- Refresh token, секрет OAuth-клиента и выданные access token вырезаются из ответов, ошибок и логов так же, как учётные данные API-клиента. Client ID OAuth-клиента — это App ID приложения, поэтому его сервер не скрывает. `auth status` и `serve --status` показывают client ID только в маске.
- `key exec` refresh token не отдаёт: для профиля со входом пользователя он работает только с `--project-id`.
- `auth logout --forget` отзывает вход в HUAWEI ID. Без `--forget` refresh token удаляется только с этой машины и действует до истечения срока (180 дней) или до снятия доступа в HUAWEI ID.

### Секреты приложений

Серверные API покупок в приложении (HMS IAP: Order service и Subscription service) не принимают API-клиент: запросы к ним подписываются токеном уровня приложения, который Huawei OAuth выдаёт по client ID и client secret приложения ([Секрет приложения](api-client.md#секрет-приложения)). Это третьи учётные данные профиля:

- client ID и client secret приложения — только в системном хранилище, учётная запись `<профиль>/app/<App ID>`; в `profiles.toml` — только список App ID (`app_secrets`). Секрет читает только клиент API сервера; в отладочном выводе он скрыт, текстового представления у него нет.
- `auth app-secret set` принимает секрет только из файла, stdin или скрытым вводом и сохраняет его только после того, как Huawei OAuth выдал по нему токен (если нет `--no-verify`). При любой ошибке ничего не сохраняется.
- Токен приложения выпускается в памяти процесса (`POST https://oauth-login.cloud.huawei.com/oauth2/v3/token`, `client_credentials`), свой у каждого приложения, заменяется за 10 минут до истечения и после ответа 401; параллельные запросы ждут одного получения. Huawei просит не получать токен перед каждым вызовом, сервер так и не делает.
- Запросы IAP уходят только на хосты IAP региона профиля (`orders-*.iap.cloud.huawei.*`, `subscr-*.iap.cloud.huawei.*`) с заголовком `Authorization: Basic base64("APPAT:" + token)`, без `client_id`. Заголовок добавляет только сервер. `api_request` ходит только в AppGallery Connect API и не может вызвать IAP или получить токен приложения.
- Приложение выбирает сервер по аргументу `appId` операции IAP; сам `appId` в Huawei не отправляется. Если секрета этого приложения нет, запрос не отправляется, а агент получает ошибку с командой `auth app-secret set`, которую пользователь запускает сам.
- Секрет приложения и его токены (как есть и в виде значения заголовка) вырезаются из ответов, ошибок и логов. `auth status` и `serve --status` показывают только, сохранён ли секрет; client ID не выводится.
- `auth logout` удаляет секреты приложений профиля; `auth app-secret remove` — секрет одного приложения.

### key exec

Gradle-плагину публикации, fastlane и своим скриптам нужны Client ID и секрет. `appgallery-connect-mcp key exec -- <команда>` отдаёт их дочерней команде, не показывая (с `--project-id` — учётные данные API-клиента проекта вместо клиента команды):

- учётные данные пишутся в новый файл (`credentials.json` или `credentials.env`) с правами 0600 в новом временном каталоге с правами 0700; в Windows вместо режимов у каталога отключается наследование прав и остаётся одна запись ACL — полный доступ текущего пользователя (по SID), а файл создаётся уже после этого и получает те же права;
- в окружение команды попадает путь к файлу (`APPGALLERY_CONNECT_CREDENTIALS_FILE` или имена из `--env`) и регион, но не Client ID и секрет; унаследованные `HUAWEI_CLIENT_ID` и `HUAWEI_CLIENT_SECRET` убираются; в аргументы команды учётные данные не подставляются;
- команда запускается без оболочки, её stdout и stderr проходят через маскировщик: секрет, Client ID, содержимое файла (как есть и в base64) и access token заменяются на `***`. Это страховка от случайного вывода, а не граница безопасности;
- файл и каталог удаляются после завершения команды при любом исходе, в том числе если команду не удалось запустить и при Ctrl-C, SIGTERM и SIGHUP. От `kill -9` защиты нет: тогда каталог останется во временном каталоге пользователя;
- в Windows команда и запущенные ею процессы работают в объекте задания (Job Object): когда команда завершилась, закрывается окно консоли или завершается сеанс, оставшиеся процессы останавливаются, чтобы файл никто не держал открытым, и файл удаляется (занятый антивирусом файл удаляется с несколькими повторами). Если `appgallery-connect-mcp` завершить принудительно (Диспетчер задач), процессы команды тоже останавливаются, но каталог останется во временном каталоге пользователя, доступный только ему.

Подробнее — [справочник CLI](cli.md#key-exec).

## Уровни доступа

- По умолчанию сервер работает только на чтение. Уровень записи (`allow_write` в профиле) включает создание и изменение: загрузку пакетов, сведения о приложении, локализации, изображения, группы подписок, сертификаты и профили. Пользователи AppGallery не видят изменения страницы и пакета, пока версия не отправлена и не одобрена.
- Уровень удаления (`allow_destructive`, включает и запись) — удаление и действия с последствиями для пользователей и денег: отправка на проверку, поэтапный выпуск и время выпуска, публичные ответы на отзывы, изменение товаров и цен, активация и деактивация товаров, акции, запись и откат Remote Configuration, удаление локализаций, сертификатов, профилей и устройств, а также подтверждение доставки покупок и отмена, отсрочка, возврат и отзыв подписок пользователей (HMS IAP). Полный список — в [MCP-инструментах](tools.md#уровни-доступа).
- Уровень доступа и каталоги `allow_path` — настройки профиля, а не регистрации в клиенте. Клиент запускает `serve --profile <имя>` без флагов доступа; флаги `serve` и `call` (`--allow-write`, `--allow-destructive`, `--allow-path`) права только сужают, а флаг, который просит больше профиля, — ошибка запуска. Поэтому правка конфигурации клиента (`~/.claude.json`, `.mcp.json`, `config.toml` Codex) прав не расширяет.
- На macOS права сверх чтения действуют только после одобрения владельцем. `appgallery-connect-mcp ui` и `connect` при повышении прав спрашивают Touch ID или пароль пользователя macOS и кладут одобренную копию прав в Keychain (сервис `appgallery-connect-mcp.access`, учётная запись — имя профиля). При запуске сервер сверяет права из `profiles.toml` с одобренными: если в файле больше, сервер работает с одобренными (без одобрения — только чтение) и пишет предупреждение в stderr. Так агент, который правит `profiles.toml`, не поднимет себе права сам.
- В Linux и Windows одобрения нет: системное хранилище там не привязывает записи к приложению, и любой процесс пользователя может их прочитать и изменить. Там права профиля действуют как записаны, а реальную границу задают роли API-клиента в AppGallery Connect: для агента, которому нужно только чтение, создайте API-клиент с ролью без прав записи ([API-клиент](api-client.md)).
- Инструменты выше разрешённого уровня не регистрируются: агент их не видит. Вызов по имени возвращает ошибку с подсказкой, как поднять уровень.
- У каждого инструмента есть аннотации `readOnlyHint` и `destructiveHint` по уровню.
- `api_request` проверяет уровень операции, которой соответствует путь; для неизвестного пути — по методу: `GET` — чтение, `DELETE` — удаление, остальные — запись.

### Почему отправка на проверку — уровень удаления

Сама отправка ничего не удаляет, но её последствия уже не в руках пользователя:

- после одобрения версия выходит к пользователям AppGallery автоматически или в назначенное время;
- отозвать отправку через API нельзя;
- поэтапный выпуск можно расширить, приостановить или завершить, но нельзя отменить, а долю пользователей — уменьшить.

Поэтому `submit_app`, `submit_app_with_file`, `release_submit` и `release_manage` доступны только на уровне удаления, а описания инструментов просят агента вызывать их только по явной просьбе пользователя и сначала с `dryRun: true`. То же для публичных ответов на отзывы и цен: их видят пользователи, а цены затрагивают деньги.

Так же и с Remote Configuration (`update_remote_config`, `rollback_remote_config`, `remote_config_set`): черновика и проверки там нет, новая версия конфигурации сразу действует для пользователей приложения, когда их устройства получают конфигурацию. `remote_config_set` по умолчанию работает с `dry_run: true` и только показывает разницу.

## Секреты в ответах

Во всех ответах агенту, включая ошибки и результаты составных инструментов, сервер заменяет на `***`:

- поля ответов, которые в спецификации отмечены как секретные: секрет приложения, содержимое `agconnect-services.json`, временные ссылки на отчёты, сертификаты и профили;
- поля паролей, секретов, токенов и ключей по имени на любой глубине (`client_secret`, `app_secret`, `access_token`, `refresh_token`, `id_token`, `code_verifier`, `authorization_code`, `api_key`, `auth_code`, `authorization` и подобные, в любом регистре и стиле имени); признаки (`has_…`, `is_…`) не трогаются;
- значения по виду в любом тексте: `Bearer …`, JWT, приватные ключи PEM, подписанные ссылки;
- известные серверу значения: секрет клиента и выданные access token, а у входа пользователя — секрет OAuth-клиента и refresh token.

Когда что-то вырезано, ответ оборачивается в `{"result": …, "note": …}`: `note` говорит, что скрыто, почему и как получить файл (`save_to`). Фильтр `jq` получает уже очищенный ответ и не может раскрыть скрытые значения.

## Что сервер не отдаёт агенту

- **Секрет приложения** (`get_app_fingerprints`, поле `secret`) не отдаётся никак: ни в ответе, ни в файл. Если он нужен, пользователь смотрит его сам в настройках проекта в AppGallery Connect.
- **Содержимое файла конфигурации** `agconnect-services.json` (`get_app_config_file`, `config_download`) — только в файл через `save_to`; в ответе путь, размер и имена ключей верхнего уровня без значений.
- **Адреса и коды загрузки** Upload Management API: шаги загрузки не стали инструментами и закрыты для `api_request`. Пакеты и изображения загружают `package_upload` и `image_sync`; адреса, заголовки загрузки и идентификаторы объектов не попадают ни в ответы, ни в ошибки, ни в логи.
- **Временные ссылки на отчёты, сертификаты и профили** — только через `save_to`: сервер скачивает файл сам. Ссылки скрываются и в ответах `api_request`.
- **Ключи подписи HarmonyOS.** Сертификат запрашивает только `certificate_request`, и только по файлу CSR (`csr_file`): CSR не передаётся текстом в аргументах, а сам запрос сертификата закрыт для `api_request`. Файл с приватным ключом (любой блок PEM `… PRIVATE KEY`) отклоняется до запроса, его содержимое не попадает ни в запрос, ни в ответ, ни в ошибку. Удаление сертификатов, профилей и устройств — уровень удаления: оно ломает подпись сборок.
- **Крупное содержимое** (отчёты, пакеты, файлы подписи) — только через файл и сводку в ответе.

Значения параметров Remote Configuration — данные разработчика, но в них бывают ключи сторонних сервисов: значения, похожие на токены, ключи и подписанные ссылки, скрываются по общим правилам. Чтобы скрытое значение не записалось обратно вместо настоящего, `update_remote_config` и `api_request` к его пути отклоняют тело, в котором есть `***`, а `remote_config_set` отклоняет такие новые значения и отправляет неизменённые параметры такими, какими их хранит AppGallery Connect (читает их сам, агенту ответ чтения не отдаёт).

Скачивание по ссылке из ответа API и отправка файлов идут только на хосты Huawei из встроенного списка (`*.huawei.com`, `*.hicloud.com`, `*.myhuaweicloud.com`, `*.dbankcloud.com` и региональные `*.dbankcloud.cn`, `.ru`, `.eu`, `.asia`), только по https на стандартный порт и без заголовков авторизации Connect API.

## Персональные данные

Отзывы и отчёт о заказах платного приложения (`paid_app_details`) содержат данные реальных пользователей AppGallery. Сервер не вырезает их: они нужны для работы с отзывами и заказами. `reviews_summary` не отдаёт данные авторов и обрезает тексты, а тексты отзывов не пишутся в логи. Инструкции сервера просят агента использовать эти данные только для текущей задачи.

### Покупки в приложении

Ответы набора `purchases` (HMS IAP) — данные покупок конкретных пользователей: номера заказов и транзакций, токены покупок и подписок, страна, сумма и валюта, время покупки и отмены, причина возврата и `developerPayload` — строка, которую приложение само передаёт в покупку (в ней может оказаться идентификатор пользователя или другая информация приложения).

- Сервер не вырезает эти данные: без токенов и номеров заказов нельзя проверить покупку или подписку. Токены покупок — не учётные данные (по ним ничего нельзя вызвать без секрета приложения), поэтому они не скрываются.
- Подпись данных покупки (`dataSignature`) сервер убирает из ответа: после разбора JSON-строки её не проверить, а проверку подписи делает бэкенд приложения.
- Тела запросов и ответов IAP (а с ними токены покупок и `developerPayload`) не пишутся в логи: в отладочном логе запроса — метод, путь и имя операции, в логе ошибки — код и текст ошибки Huawei.
- Инструкции сервера просят агента использовать данные покупок только для текущей задачи и не копировать их в файлы, коммиты и сообщения, а инструменты, которые меняют деньги или доступ пользователя (подтверждение доставки, отмена, отсрочка, возврат и отзыв подписки), — уровень удаления: агент вызывает их только по явной просьбе пользователя.

## Фильтр jq

Фильтр выполняется в отдельном процессе того же бинарника с пустым окружением и таймаутом 10 секунд: ему недоступны переменные окружения, файлы, хранилище учётных данных и сеть, а зависание или переполнение стека завершают только этот процесс. Синтаксис фильтра проверяется до запроса к API.

## Пользовательские инструменты

Файлы пользовательских инструментов — доверенная конфигурация пользователя. Автоматически читается только `tools.toml` в каталоге настроек; другие файлы (например, из репозитория проекта) — только явным `--tools-file`. Пользовательский инструмент вызывает обычную операцию API через те же проверки: схема аргументов, уровень доступа операции, вырезание секретов. Фиксированные аргументы агент переопределить не может, имя, совпадающее со встроенным инструментом, — ошибка запуска.

## Локальные файлы

Аргументы с путями (`file` у `package_upload`, `csr_file` у `certificate_request`, `dir` у инструментов страницы приложения, `save_to`) работают только с путями внутри разрешённых каталогов (`FilePolicy`):

- рабочий каталог сервера, если это не корень файловой системы и не домашний каталог;
- системный временный каталог: он разрешён для черновых файлов и скачиваний, но общий для всех программ пользователя, поэтому не держите в нём ничего личного;
- каталоги `allow_path` профиля (на macOS — одобренные, каталог должен существовать); `serve --allow-path` оставляет из них только указанные.

Пути проверяются после раскрытия `..` и символических ссылок: ссылка, которая ведёт за пределы разрешённых каталогов, отклоняется. Относительный путь считается от рабочего каталога сервера. Существующие файлы никогда не перезаписываются: для скачивания нужен новый файл; недописанный файл удаляется. Единственное исключение — `.appgallery-images.json` в каталоге страницы, который `image_sync` заменяет новым. Путь для `save_to` проверяется до запроса к API.

Не разрешайте каталоги с ключами и секретами (`~/.ssh`, хранилища ключей подписи, файлы с секретом API-клиента): агент сможет загрузить из них файл в AppGallery Connect.

## Протокол и логи

- stdout занят протоколом MCP; логи и диагностика пишутся только в stderr. Уровень — `--log-level`, иначе `RUST_LOG`, иначе `warn`. Секрет, токен, адреса загрузки и тексты отзывов в логи не попадают.
- Ошибки AppGallery Connect API (`4xx`, `5xx` и ненулевой код результата при HTTP 200) и запрещённые вызовы возвращаются агенту как результат инструмента с `isError: true`; процесс не падает. Тело ошибки обрезается и проходит вырезание секретов.
- В режиме stdio сервер не открывает сетевых портов; HTTP-режим слушает только адрес `--listen` ([HTTP-режим](#http-режим)). Сервер ходит только в AppGallery Connect API своего региона и на хосты Huawei для загрузки и скачивания файлов.

## HTTP-режим

`serve --http` открывает сетевой порт, поэтому у него свои границы ([HTTP-режим и Docker](http.md)):

- Учётные данные API-клиента остаются на сервере: системное хранилище профиля или файл секрета `--secret-file`. Клиенты их не присылают и не получают; access token Huawei один на всех клиентов и живёт в памяти процесса.
- Вход пользователя (профиль `auth login --oauth` на машине сервера) тоже остаётся на сервере: refresh token — в системном хранилище машины сервера, туда же сохраняется новый. Все клиенты работают от имени этого пользователя в команде профиля, поэтому раздавайте токены доступа только тем, кому этот пользователь доверил бы свою роль.
- Файл секрета принимается, только если это обычный файл без прав для группы и остальных (`0600` или `0400`); права проверяются у открытого файла. Содержимое и путь к нему не попадают в ответы и логи. Флаг есть только в Linux и macOS.
- Клиент проходит по токену доступа в `Authorization: Bearer`. Сервер хранит только SHA-256 токенов, сравнивает их за постоянное время, токен короче 32 символов не принимает. Заголовок `Authorization` дальше обработчика MCP не передаётся, в логах — только имя токена.
- У каждого токена свой уровень доступа и наборы; уровень сервера — потолок. С учётными данными из хранилища это права профиля (на macOS — одобренные), суженные флагами `--allow-write` и `--allow-destructive`: флаг сверх профиля — ошибка запуска. С `--secret-file` уровень задают одни флаги. Инструменты выше уровня токена ему не видны и не вызываются, `api_request` тоже ограничен уровнем токена.
- Адрес по умолчанию — `127.0.0.1:8769`. Заголовок `Host` проверяется (защита от DNS rebinding), запросы браузера с `Origin` отклоняются, пока он не разрешён `--allowed-origin`. Тело запроса ограничено `--max-request-bytes`.
- Сервер говорит по обычному HTTP: вне loopback ставьте его за reverse proxy с TLS или в закрытую сеть.
- Файлы машины агента серверу недоступны. Инструменты с файлами работают только с каталогами сервера (`allow_path` профиля, суженные `--allow-path`, а с `--secret-file` — каталоги `--allow-path`), без них они не регистрируются; рабочий и временный каталоги сервера не разрешаются.
